# Evaluate Mojo expressions in LLDB

## Motivation

`expression --language mojo` reuses the Mojo REPL parsing and lowering path.
That path had no connection to LLDB's selected stack frame or to LLDB's result
materialization, so an expression such as `lhs + rhs` could not resolve `lhs`
and `rhs`, and a bare expression that did compile was rewritten by Mojo's
unused-value fix-it into `_ = lhs + rhs`, leaving LLDB with no value to display.

This change connects the three pieces so that a bare expression consumes frame
locals and produces an ordinary LLDB result:

```text
(lldb) expression --language mojo -- lhs + rhs
(Int) $R0 = 42
```

## How it works

### Frame locals reach the parser

`MojoUserExpression::Parse` creates its parser with the selected frame as the
execution scope, falling back to the process when there is no frame. A `Process`
can calculate the target, but it cannot calculate the frame whose locals the
expression has to resolve.

`MojoExpressionParser::parse` then collects the in-scope variables of that frame
and passes them to the REPL wrapper ahead of the persistent REPL variables, so a
frame local shadows a persistent variable of the same name.

Only the frame variables the expression actually references are materialized.
The parser first performs a structural discovery pass with every usable frame
variable available as a generated argument. A parser listener records source
references that resolve to those arguments, excluding references that resolve
to declarations in the expression itself as well as identifier-like text in
comments and strings. The expression is then parsed for execution with only
the selected frame arguments and the persistent REPL variables.

The discovery pass matters because the generated context struct is laid out
when the expression is compiled. Materializing every in-scope frame variable
would make evaluation depend on unrelated variables that the user never
referenced, and would make the wrapper unnecessarily large.

Variables are skipped when they are artificial, have no valid location, are file
globals, carry a name generated by the expression wrapper (`__lldb*`,
`__mojo_repl*`), or have a type the expression context cannot import.

Names and types come from `StackFrame` and `ValueObject` rather than from
`Variable` directly: some lower-level `Variable` methods are not exported by
`liblldb`, and staying on the public interface keeps the loadable plugin linked
only against supported LLDB symbols.

### Types cross MLIR contexts by spelling

Debug-info types belong to a module-specific `MLIRContext`, while expression
parsing uses the target's scratch `MojoTypeSystem`. Passing the original
`mlir::Type` across would mix context-owned objects, so each type is printed and
reparsed in the expression context.

A raw `!kgen.scalar` type describes a variable's ABI but carries no Mojo
methods, which makes `x + y` fail type checking.
`recoverProgramVariableSourceType` maps the scalar storage types back to
source-level `Int`, `UInt`, and `Bool`. It applies only to the leading
`numProgramVariables` entries — persistent REPL variables already carry
source-level types — so the shared REPL, Jupyter, and LSP paths are
unaffected.

The recovery is intentionally limited to the scalar builtins whose debug
representation is currently known. Richer types should get a general source-type
encoding in debug information rather than an expanding list of guesses in the
debugger.

### Two pointer layouts in one wrapper

The REPL wrapper distinguishes program variables from persistent REPL variables
through the `numProgramVariables` boundary. Program variables use `Pointer[T]`,
matching what `Materializer::AddVariable` writes into the context struct;
persistent variables keep the existing `Pointer[Pointer[T]]` layout, because
they need an allocation whose address survives the expression. Existing REPL and
LSP callers are unchanged through the parameter's default value of zero.

### Bare expressions produce a result variable

When the parser reports the unused-value fix-it for a bare expression,
`LLDBMojoREPLListener` classifies the parser's fix-its as passthrough, an
internal result rewrite, or a result rewrite combined with a user-visible
correction. Only a single diagnostic whose sole fix-it inserts `_ = ` is
internal. The listener replaces that discard with
`var __lldb_expr_result = ` and reparses it directly, avoiding LLDB's generic
"Evaluated this expression after applying Fix-It(s)" announcement for an
implementation detail.

Every other fix-it still goes through `MojoUserExpression::setFixedText`, so
corrections such as adding `()` or `await` retain LLDB's normal announcement.
If such a correction accompanies the result rewrite, the listener accounts for
the length of preceding edits when locating `_ = ` in the combined text. If the
location cannot be validated, it passes the parser's fixed text through
unchanged.

That variable is backed by `Materializer::AddResultVariable`, so LLDB
dematerializes and prints it as `$R0`, `$R1`, and so on.
`MojoPersistentExpressionState::GetNextPersistentVariableName` supplies those
names.

Because an LLDB result already has storage supplied by the materializer, its
output field is a single pointer and no additional allocation is emitted for it.
Results are kept distinct from persistent REPL references: they live in the
persistent state so LLDB can print them, but they are not passed as inputs to a
later Mojo expression.

### Struct layout and materializer order must agree

The generated context struct is laid out as:

```text
[ program variables ][ persistent inputs ][ output fields, sorted by name ]
```

`Materializer` entities are assigned offsets in the order they are added, so
`prepareForExecution` has to register entities in exactly that order or the
dematerialized values are read from the wrong offsets. Three things enforce it:

- Frame variables are registered first, in collection order.
- `MojoPersistentExpressionState::forEachInputVariable` is the single
  definition of which persistent variables are inputs and in what order. `parse`
  builds the parser's input list through it and `prepareForExecution` registers
  materializer entities through it, so the two cannot drift.
- The result variable is just another output field, so it is sorted together
  with the new persistent variables under the same comparator
  `processVariablesForPersistence` uses, rather than relying on
  `__lldb_expr_result` happening to sort where it is needed.

The input fields are registered even when `keepResultInMemory` is false. The
struct's layout was fixed at compile time, so skipping them would leave the
compiled code reading fields that were never materialized; only the output
fields depend on anything outliving the evaluation.

### Optimization level

Debugger expressions compile against a private copy of the target's compilation
options with optimization level `0`, which preserves the stores and temporary
values that result materialization depends on. REPL cells go through the same
parser but have no materialized result, so they keep the target's optimization
level; lowering it there would be a large and pointless performance regression.
Neither path changes the target's global compiler configuration.

## What evaluates today

Measured against the categories LLDB's C++ expression tests cover:

| Category | Status |
| --- | --- |
| Frame locals, alone and through operators | works |
| Literal expressions naming no local | works |
| Arithmetic `+ - * //`, unary `-` | works |
| Comparisons and `and` / `not` | works |
| `Int`, `UInt`, `Bool` locals | works, source type recovered |
| `Float64` locals | works, reported as its storage type |
| `String` locals, including method calls | works |
| Several statements separated by `;` | works, last one is the result |
| Successive result variables `$R0`, `$R1`, … | works |
| Member access / methods on a program-defined struct | not supported |
| Subscripting a list | not supported |
| Calling a program function | not supported |
| `comptime` module constants | not supported |
| Assignment to a frame local | not supported |
| Naming an LLDB `$R0` from a Mojo expression | not possible |

Most unsupported cases share one cause: a frame variable's type is carried from
debug information into the expression context by printing it and reparsing it
there, and some types come back opaque as `AnyStruct[...]`, leaving member
access, methods, and subscripting nothing to resolve against. A plain stdlib
struct such as `String` survives that round-trip and its methods work —
`text.byte_length() + lhs` evaluates. A parameterized one such as `Array[Int]`,
and anything declared in the program's own module such as `Point`, do not; for
the latter the parser also reports that it cannot locate the program module.
Fixing this needs a general source-type encoding in debug information rather
than more special cases in the debugger. `frame variable point.x` reads the
same field without the expression evaluator and does work.

Two cases are separate. Assignment parses and runs, but the materializer cannot
write the value back. And `$R0` cannot be *named* from a Mojo expression at all:
`$` is not a valid Mojo lexeme, so reading a previous result back fails in the
lexer rather than in name lookup.

Note that `len(text)` is rejected by Mojo itself, not by the debugger: a UTF-8
string has no single length, and the diagnostic points at `byte_length()`,
`codepoints()`, and `graphemes()` instead. Those all evaluate.

## Current limitations

- Source-level type recovery covers scalar `Int`, `UInt`, and `Bool`. Other
  debug-info storage types are used unchanged and may not support source-level
  operators.
- Artificial variables, variables without a valid location, and file globals are
  not added to the expression context.
- The set of frame variables is fixed when the expression is parsed. A parsed
  expression re-executed against a different frame — a breakpoint condition,
  for example — materializes the variables of the frame it runs in, but its
  inputs were chosen from the frame it was parsed in.
- LLDB result variables are deliberately not accepted as implicit inputs to
  later Mojo expressions; persistent Mojo REPL variables continue to use the
  existing reference representation.

## Testing

`KGEN/test/mojo-debug/expression.lldb` runs the debugger over
`Inputs/expression.mojo` and covers every row of the table above that works:
frame locals through operators, a literal expression naming no local, the
arithmetic and comparison and logical operators, one local of each reaching
type, successive result names, and the absence of the fix-it banner.

`KGEN/test/mojo-debug/expression-unsupported.lldb` pins the rows that do not
work, asserting on the diagnostic each one produces. It exists so the failures
stay diagnostics rather than silence, and so that the day one of them starts
working shows up in the diff. Each case needs its own run — `-b` abandons the
remaining `-o` commands once one reports an error — and `not`, because a
failed expression makes the debugger exit non-zero.

```bash
./bazelw build //KGEN:MojoLLDB --config=build-mojo
./bazelw test //KGEN/test/mojo-debug:test --config=build-mojo
```

`KGEN/lib/MojoTooling/ParserDriverREPL.cpp` is shared with the REPL, Jupyter,
and LSP front ends, so those suites are part of the change's test surface:

```bash
./bazelw test //KGEN/test/mojo-repl/... //KGEN/test/mojo-jupyter/... \
    --config=build-mojo
```

## Repository conventions

`KGEN/` is not one of the areas open to external contribution. `CONTRIBUTING.md`
lists the Mojo standard library, MAX, the MAX accelerator library, the example
directories, and the Mojo documentation; `mojo/CONTRIBUTING.md` records that the
Mojo compiler has no contribution process defined yet. This work therefore lands
internally rather than as a community pull request.

Two conventions still apply to it and are not yet met:

- `mojo/CONTRIBUTING.md` asks that changes over 100 lines be split. This one is
  well over that and divides cleanly into the wrapper layout plus frame-variable
  collection, the result-variable materialization, the scalar source-type
  recovery, and the optimization-level change.
- This file is a working document at the repository root, alongside
  `lldb_01.md`, `lldb_02.md`, and `lldb_03.md`. The rationale belongs in the
  commit message and pull request description, and any lasting design notes
  belong under `KGEN/docs`.
